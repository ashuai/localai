# 模型层设计论证:小上下文 · 零成本 · 频繁微调用

> 服务器:192.168.0.5:9870 上的本地 oMLX v0.4.4(Qwen3.6-35b,Apple Silicon)
> 一句话结论:**既然每次调用近乎免费且只有 1-2 秒,智能的最小单位就该是一次
> 小上下文的有界调用,而不是一条不断膨胀的长上下文。** 本层把"一次调用"
> 定义为可组合的微调用原语,由确定性的 Rust 代码编排。

---

## 1. 前提与实测数据(2026-08-16 实测)

| 项 | 实测值 | 影响 |
|---|---|---|
| 稳态单次小调用 | **1.06 - 1.81s**(server total_time) | 微调用 fan-out 完全可承受 |
| 模型冷加载 | +16s(一次,之后常驻) | 启动后首个请求慢,后续稳定 |
| 主模型 | `Qwen3.6-35b`(is_default,MoE 3B active) | 默认模型;`Qwen3.5-27b` 是 Claude 蒸馏模型(输出带 tool 包裹),非必要不用 |
| JSON 模式 | `response_format: json_object` 支持 | 结构化输出,机器可直接消费 |
| 关思考 | `chat_template_kwargs.enable_thinking: false` **必须** | 默认开思考会把推理过程混进 content,JSON 模式还会变成 `default_api.assistant` tool 包裹;关掉后输出干净 |
| 提示词缓存 | usage 有 `cached_tokens` 字段 | 稳定前缀可命中 oMLX 的 hot/SSD 缓存(16GB/92GB) |
| 并发 | 服务器 `max_concurrent_requests: 12`(continuous batching) | 客户端并发上限 6,留余量 |
| 上下文 | 模型声明 262k,但受 Apple Silicon 内存守卫限制 | 按"小上下文"原则设计,绝不依赖长上下文 |

## 2. 前提推演:免费 + 快 + 小,意味着什么

把三个事实放在一起:

1. **零成本**:没有 token 计费,重试、冗余调用、多角度验证都不心疼;
2. **快**:1-2 秒/次,串行 4 次 ≈ 4-8 秒,并行 fan-out 可压到 2 秒级;
3. **小**:上下文宝贵,塞不下"整个会话 + 所有工具 + 长文档"。

推论 A —— **重试是免费的正确性工具**:JSON 解析失败、格式漂移,直接重试 2 次,
比任何"让它别出错"的提示工程都可靠(实测 Qwen3.6-35b + json_object + 关思考,
干净率接近 100%,重试只是兜底)。

推论 B —— **分解优于内聚**:一个复杂任务拆成 N 个小调用,每个调用只装"一件事"
的最小输入 + 固定任务模板。总 token 成本与单次大调用相当或更少,但:
- 每步输出可独立校验、可独立重试;
- 中间结果以 Rust 结构物化,错误边界清晰;
- 任何一个子任务的失败不会污染整条上下文。

推论 C —— **确定性编排 + LLM 微决策**:LLM 只做"分类、抽取、生成"这类微决策,
流程控制(先后、分支、fan-out、聚合)全部由 Rust 代码决定。LLM 不负责"记得自己
做到哪了" —— 状态在 Rust 侧,上下文永远只装当前这一步。

推论 D —— **缓存友好**:固定系统提示词 + 稳定任务模板 = 前缀稳定,吃 oMLX 的
prompt 缓存;有界小上下文让 KV cache 常驻 hot cache,连续微调用越来越快。

## 3. 微调用协议(代码落地:src/llm/micro.rs)

```rust
MicroTask { name, system, input, max_tokens }
    → MicroOutcome { json, text, latency_ms, retries }
```

- `system` = 固定任务模板(不变 → 缓存命中);
- `input` = 这一件事的最小载荷(绝不带历史);
- 每次调用固定:JSON 模式 + 关思考 + 有界 max_tokens;
- 失败重试:解析失败重试(默认 2 次),全程有信号量限流(默认并发 6)。

内置任务模板示例(plugins/microtask.rs):
- `classify` 意图分类:`{"intent": "question", "confidence": 0.9}`
- `tags` 关键词:`{"tags": ["天气", "查询"]}`
- `title` 标题:`{"title": "..."}`
- `summary` 摘要:`{"summary": "..."}`

## 4. 编排模式(两个落地范式)

### 4.1 环境微调用(ambient micro-calls)
每次主回复完成后,并行 2 个微调用(意图分类 + 关键词)做"零成本增值"——
回答照常渲染,旁边多一行 `[micro] 意图=question | 关键词=天气,查询 (1.2s)`。
**这就是"什么小事都能调用"的形态:一次对话,附带几次免费的小调用。**

### 4.2 流水线(fan-out pipeline,`/micro` 命令)
```
输入 → [阶段1: classify] 串行决策(1 次调用)
     → [阶段2: title + tags + summary] 并行 fan-out(3 次调用,信号量内)
     → 聚合为结构化行 + 分阶段耗时
```
串行部分只做"决策",并行部分做"互不依赖的抽取",最后确定性聚合。

## 5. 为什么不用"大上下文长循环"(对比 DSH agent loop)

DSH 的 agent loop 依赖大上下文(会话 + 工具 + 技能),适合云端大模型;本项目的
本地 LLM 前提不同:

| 维度 | 大上下文长循环 | 小上下文微调用(本项目) |
|---|---|---|
| 上下文 | 随会话无限增长,内存守卫风险 | 每次调用有界(≤ 任务模板 + 载荷) |
| 失败 | 中间污染整条上下文,回滚难 | 单调用失败,重试/丢弃即可 |
| 并发 | 单请求串行 | 互不依赖子任务可并行(12 并发) |
| 缓存 | 前缀漂移,缓存命中差 | 稳定前缀,命中 hot/SSD 缓存 |
| 成本 | (云端)贵,要省着用 | 零成本,放手用 |
| 心智 | 模型要"记住"进度 | 进度在 Rust 侧,模型只做单步决策 |

**适用边界**:微调用模式适合"决策/抽取/生成小块内容";需要多轮反思、长文写作时,
退化为 chat 插件的有界滚动历史(最近 N 轮,系统提示词恒定)。

## 6. 上下文纪律(chat 插件落地)

- 系统提示词固定(`CHAT_SYSTEM` 常量 → 缓存友好);
- 滚动历史有界:`history_turns`(默认 6 轮),超过即裁剪头部,绝不无限累积;
- 模型层不做跨调用状态,历史是插件的业务状态(内存中,可选持久化)。

## 7. 失败处理与可观测

- **重试**:JSON 解析失败重试 2 次(零成本;见推论 A);
- **降级**:`extract_json` 容忍围栏/前后缀/裁剪,取 `{...}` 子串兜底;
- **限流**:`Semaphore(max_concurrent=6)` 客户端全局,防打满服务器 12 并发;
- **可观测**(v1 最小):`SessionStatus` 事件输出每次调用的耗时;
  演进:usage(总耗时/缓存 token)落日志,形成"每次微调用的成本台账"。

## 8. 演进方向

1. **约束解码**:oMLX 支持 `guided_grammar` / `structured_outputs` —— 把 JSON 校验
   从"解析后重试"前移到"生成时约束",干净率提到 100%、省一次重试;
2. **微调用缓存**:同 task+input 的幂等调用(如摘要)落 KV 缓存,直接命中;
3. **embedding 增值**:bge-m3 已就绪,可做微调用结果的语义去重/聚类;
4. **工作流插件**:把 4.2 的流水线推广为可声明的工作流(链式 + 并行 + 条件分支),
   每个节点都是微调用 —— 即"技能层"的本地版。
